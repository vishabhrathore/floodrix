# FloodRix — Project Bible

> **What this document is:** The single source of truth for the entire project. Read this before touching any code. It explains what the project is, why every file exists, what happens inside each one, and the order in which they should be built.

---

## What is FloodRix?

FloodRix is a no-code civil engineering hydraulics platform. Engineers build calculation workflows visually on a React Flow canvas — dragging formula nodes, lookup tables, interpolation curves, and decision branches — then run them to compute flood discharge, scour depth, waterway width, and other bridge design parameters per Indian Roads Congress (IRC) standards.

The system has two canvases. The **workflow canvas** is where computation graphs are built — INPUT nodes collect site data, FORMULA nodes evaluate math expressions, LOOKUP TABLE nodes find coefficients, DECISION nodes branch on conditions, and DISPLAY nodes compare results and select the design value. The **workspace canvas** is where engineers organize their workflow library into a folder tree — Flood Discharge → Empirical → Indian Formulas → Dicken's — and link calculation workflows at the leaves.

Workflows can be run interactively (pausing at INPUT nodes for user values) or in batch mode (processing 50+ sites from an Excel file in the background). Every formula and coefficient table lives in a shared registry with version pinning. Every change is audit-logged. Every execution is saved for history and comparison.

## Tier 0 — Foundation (build first, everything depends on these)

These files must exist before any feature code can run. They provide database access, authentication, API infrastructure, and type safety.

### `prisma/schema.prisma`

**Status:** ✅ Built
**Priority:** Critical — every other file reads from or writes to this schema.

The complete database schema with 26 tables and 15 enums. Defines the data model for workflows, nodes, edges, variables, registries, workspaces, execution sessions, batch jobs, and audit logs. Every Prisma query in the codebase is type-checked against this file. Changing a column here ripples through the entire system.

Key design decisions baked into this file: workspace nodes use adjacency list with materialized path for tree queries. Workflow variables have three-layer identity (contextKey, displayLabel, notation). Registry items support version pinning through a separate versions table. Node configs are stored as JSONB with structure varying by NodeType enum. Execution sessions track pause state via currentNodeId and pauseReason.

### `src/generated/prisma/`

**Status:** Auto-generated (gitignored)
**Priority:** Critical — Prisma client output.

Generated by `npx prisma generate`. Contains the typed Prisma Client, all model types, and enum types. Never edit manually. Regenerate after every schema change.

### `src/lib/db.ts`

**Status:** ✅ Built
**Priority:** Critical — every server-side file imports this.

Prisma client singleton using the `globalThis` pattern to survive Next.js hot reloads in development. Without this, each hot reload creates a new database connection pool until Postgres runs out of connections.

```typescript
import { PrismaClient } from "@/generated/prisma";

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient };
export const db = globalForPrisma.prisma || new PrismaClient();
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = db;
```

## Tier 1 — Engine (core computation, must work before any UI)

These files contain the business logic that makes FloodRix a calculation platform rather than just a canvas editor. They run on the server, process math, manage state machines, and talk to the database.

### `src/server/engine/units.ts`

**Status:** ✅ Built
**Priority:** Critical — every value in the system passes through unit conversion.

The unit registry and conversion system. Defines 50+ units across 13 dimensions (length, area, discharge, rainfall, velocity, etc.). Each dimension has one canonical unit that matches IRC codebook conventions (Km² for area, Cumecs for discharge, cm for rainfall). Exports `convertUnit()`, `toCanonical()`, `fromCanonical()`, and `processInputValues()`.

The core principle: values enter as whatever unit the user chose (hectares, cusecs, mm), get converted to canonical at the INPUT boundary, flow through formulas as raw numbers, and get converted back to display units at the OUTPUT boundary. Formulas never think about units.

Also exports `parseColumnHeader()` and `buildBatchColumnMapping()` for detecting units from Excel column headers like "Area (ha)" and auto-converting during batch processing.

### `src/server/engine/interpolation.ts`

**Status:** ✅ Built
**Priority:** High — GRAPH_INTERPOLATION nodes depend on this.

1D interpolation (linear, cubic spline, step) and 2D bilinear interpolation for digitized codebook curves. The `interpolate()` function takes an array of (x, y) points, an x value, and an interpolation method, and returns the interpolated y value. Handles extrapolation (clamp, extend, error).

The cubic spline implementation builds a natural cubic spline using a tridiagonal system solver — this gives smooth curves through the digitized points, which is essential for accurately reading IRC figures like the Areal Reduction Factor curve (Fig 4.2, IRC:SP:13-2004).

### `src/server/engine/registry-resolver.optimized.ts`

**Status:** ✅ Built
**Priority:** Critical — every FORMULA and LOOKUP_TABLE node that references the registry uses this.

Factory function `createRegistryResolver()` that returns a per-execution-context resolver with an internal cache. Resolves formula and table registry references, handles version pinning (float to latest vs. pin to specific version), and supports batch prefetching.

Key method: `prefetchForWorkflow()` loads ALL registry items used by a workflow in 2-3 queries (one for formulas, one for tables, optionally one for pinned version snapshots), then warms the cache. Every subsequent `resolveFormula()` or `resolveTable()` call during execution is a zero-query cache hit.

The resolver also implements `getImpactAnalysis()` — given a registry item, it finds every workflow that references it and categorizes them as "floating" (will be affected immediately by an update) or "pinned" (safe but outdated).

### `src/server/engine/workflow-executor.ts`

**Status:** ✅ Built
**Priority:** Critical — this IS the product. Without this, nothing computes.

The core execution engine. Contains:

- `resolveExecutionOrder()` — topological sort using the `toposort` library. Takes nodes and edges, returns an ordered array of node IDs. Detects cycles and throws a clear error.

- `WorkflowExecutor` class with three entry points:
  - `startExecution()` — creates a session, resolves execution order, creates NodeExecution records, begins the loop.
  - `resumeWithInput()` — called when the user submits values at a paused INPUT node. Merges values into the variable context, marks the node complete, continues execution.
  - `cancelExecution()` — marks session as cancelled, skips all pending nodes.

- `continueExecution()` — the core loop. Walks the sorted node list. For each node, dispatches to the appropriate handler based on `node.type`. If an INPUT node needs user values, writes `status: PAUSED` and `currentNodeId` to the session and returns to the frontend. Non-input nodes execute instantly.

- Individual node executors: `executeFormula()` (handles registry resolution and variable binding), `executeLookup()` (range/exact match), `executeInterpolation()` (delegates to interpolation.ts), `executeDecision()` (evaluates condition, computes skip set for false branch), `executeDisplay()` (comparison + IRC Article-6 selection logic), `executeValidation()` (constraint checks).

Every node executor writes its result to the `variables` JSONB on the session. Every step is recorded as a `NodeExecution` row with input vars, output vars, computation details, and timing.

### `src/server/engine/batch-executor.ts`

**Status:** ✅ Built
**Priority:** High — enables processing 50+ sites at once.

Two parts:

1. `BatchExecutorService` — creates batch jobs, tracks progress, returns results. The `createBatchJob()` method creates the job and row records, then fires an Inngest event to start background processing. The frontend polls `getProgress()` every 2 seconds.

2. `processBatchJob` — the Inngest function that runs in the background. Loads the workflow once, processes rows in chunks of 10 (for progress updates), and calls `WorkflowExecutor.startExecution()` for each row with pre-filled input values. The key trick: batch mode pre-fills all INPUT node values from the CSV row, so `allProvided` returns true and the executor never pauses.

### `src/server/engine/audit-service.ts`

**Status:** ✅ Built
**Priority:** High — every change and execution is logged here.

Central audit logging service with five methods:

- `log()` — single audit event
- `logBatch()` — multiple events sharing one batchId (for canvas saves)
- `logNodeChanges()` — accepts add/remove/modify/move arrays from canvas diff, creates grouped audit entries
- `query()` — filtered paginated query with user/workflow/resource/action/date filters
- `getWorkflowTimeline()` — groups by batchId, generates human-readable summaries ("added 3 nodes, modified 1")
- `getExecutionHistory()` — user's past runs with workflow name, status, duration, node counts
- `getSessionDetail()` — full step-by-step execution record for a single session

### `src/server/engine/canvas-save.ts`

**Status:** ✅ Built
**Priority:** High — saves the workflow canvas to the database.

Two functions:

- `saveCanvas()` — diffing-based save. Loads existing nodes + edges, compares against new React Flow state, categorizes changes into added/removed/modified/moved, applies minimal batch operations in one transaction, and logs audit entries. (Note: the optimized version in `canvas-queries.ts` supersedes parts of this.)

- `publishWorkflow()` — creates an immutable version snapshot. Serializes all nodes, edges, variables, and metadata into a JSON blob stored in `workflow_versions`. Increments the version number and sets status to PUBLISHED.

### `src/server/engine/index.ts`

**Status:** ✅ Built
**Priority:** Convenience — central export barrel.

Re-exports everything from the engine modules. Importing `from "@/server/engine"` gives you the executor, resolver, audit service, batch executor, interpolation, units, and canvas save functions.

### `src/server/engine/formula-validator.ts`

**Status:** Not yet built
**Priority:** High — security gate for user-written formulas.

Parses mathjs expressions into an AST and validates them before storage. Blocks dangerous functions (`import`, `evaluate`, `parse`, `compile`), allows only safe math functions (`sqrt`, `pow`, `abs`, `log`, `sin`, `cos`, `min`, `max`), prevents assignment expressions and property access, and extracts the list of variable names used in the expression. Returns `{ valid, error, variables }`.

Also exports `evaluateFormula()` — a sandboxed mathjs evaluator that creates a restricted scope with only the provided variables, no access to globals.

## Tier 2 — Database & API Layer (queries, routers, optimizations)

These files bridge the engine to the frontend through optimized database queries and tRPC procedures.

### `src/server/db/canvas-queries.ts`

**Status:** ✅ Built
**Priority:** High — makes canvas saves fast.

Optimized save logic that supersedes the naive approach in `canvas-save.ts`:

- `saveCanvasOptimized()` — in-memory diff that categorizes nodes into create/update/delete buckets. Only creates new nodes (`createMany`), updates dirty fields on modified nodes (skips position-only changes on the fast path), and deletes removed nodes. A "just moved 5 nodes" save goes from 45 queries to 8.

- `loadWorkflowForExecution()` — two-phase load with parallel queries. Loads workflow metadata, nodes, edges, and variables in 4 concurrent queries instead of one massive include.

- `SessionStateBuffer` — holds session progress in memory, only flushes to DB every N nodes (configurable). Cuts session progress writes from 17 to 4 for a typical workflow.

### `src/server/db/workspace-queries.ts`

**Status:** ✅ Built
**Priority:** High — makes folder tree operations fast.

Optimized workspace tree operations:

- `loadWorkspaceTree()` — single `findMany` with `include: { linkedWorkflow }`, sorted by depth + sortOrder. Builds parent→children map in memory.
- `loadSubtree()` — recursive CTE with depth limit for lazy-loading deep trees.
- `moveWorkspaceNode()` — single raw UPDATE with `CASE` expressions for path rewrite + reparent + reorder, instead of multiple sequential queries.
- `getChildCounts()` — groupBy aggregation query for folder badges ("3 subfolders · 2 workflows") without loading full rows.
- `reorderSiblingsSafe()` — batched transaction for drag-reorder.

### `src/server/db/indexes.ts`

**Status:** ✅ Built
**Priority:** Important — documents all composite indexes.

Reference file containing the optimized index definitions for every table. Not executable code — it's a guide for what indexes to add to schema.prisma. Includes before/after comparisons showing why composite indexes like `@@index([userId, createdAt(sort: Desc)])` outperform single-column indexes for common queries.

### `src/server/routers/workflow.ts`

**Status:** ✅ Built
**Priority:** Critical — all workflow CRUD flows through here.

tRPC router with procedures: `list` (paginated, filtered by status/category), `get` (single workflow with nodes + edges + variables), `create`, `update` (metadata only), `saveCanvas` (delegates to canvas-queries), `publish` (delegates to canvas-save.ts), `delete`, `duplicate`.

### `src/server/routers/execution.ts`

Three merged routers in one file:

- **Execution router:** `startRun`, `submitInput`, `cancelRun`, `getSession`, `getHistory`, `rerun`, `compareSessions`.
- **Audit router:** `getTimeline`, `query`, `getNodeHistory`.
- **Batch router:** `createJob`, `getProgress`, `getResults`, `cancel`, `listJobs`.

## Tier 3 — Frontend Stores & Canvas Infrastructure

These files provide the reactive state management that drives both canvases.

### `src/features/workspace-canvas/workspace-canvas-store.ts`

**Status:** ✅ Built
**Priority:** Critical — drives the entire workspace folder editor.

Zustand store that holds workspace data in DB shape (`dbNodes[]` with `parentId`) and derives React Flow state (rfNodes + rfEdges) from it. Key design: edges don't exist in the database — they're derived from parentId relationships.

All operations (create folder, move, delete, connect, rename) modify `dbNodes[]` in memory with optimistic updates. A debounced `flush()` function batches all changes into one tRPC call every 1.5 seconds (3 seconds for position-only changes). Result: 2 database calls for an entire editing session (1 load + 1 save).

### `src/features/workflow-canvas/workflow-canvas-store.ts`

**Status:** Not yet built
**Priority:** Critical — drives the calculation flow editor.

Similar to workspace-canvas-store but for computation workflows. Holds nodes and edges in React Flow shape (since workflow edges ARE real database rows, unlike workspace edges). Manages dirty tracking, debounced save, undo/redo stack.

Key difference from workspace store: this store also manages the variable registry — when a formula node is added, the store auto-creates workflow variables for its inputs and outputs, detects notation collisions, and resolves bindings.

### `src/features/workflow-canvas/nodes/theme.ts`

**Status:** ✅ Built
**Priority:** High — design tokens for all 20 node types.

Three registries:

1. `HANDLE_COLORS` — maps data types (number, string, boolean, table, curve, dataset, any, trigger) to colors. Blue handles = numeric data, purple = table data, pink = curve data, gray = any/trigger.

2. `NODE_ACCENTS` — maps each of the 20 node types to an accent color, background tint, display label, and Lucide icon name.

3. `NODE_HANDLES` — defines the input and output handles for each node type with their data types and positions. A DECISION node has one input (number, left) and two outputs (trigger:true, trigger:false, right). A FORMULA node has one input (number, left) and one output (number, right).

### `src/features/workflow-canvas/nodes/base/base-node.tsx`

**Status:** ✅ Built
**Priority:** High — shared wrapper for all 20 node types.

Renders the card container that every node type sits inside: left accent border (colored by node type), header (icon + label + subtitle + type badge + context menu), body (children — type-specific content), footer (optional reference citation), and input/output handles (positioned from NODE_HANDLES config).

Also renders execution status: a colored dot in the header that animates (pulse) when the node is running, turns green when completed, red when errored, and blue when waiting for user input.

Every node type renders ONLY its body content and passes it as `children` to BaseNode. Layout, selection state, hover effects, handle positioning, and the context menu (configure, duplicate, delete) are all owned by BaseNode.

### `src/features/workflow-canvas/nodes/base/node-handle.tsx`

**Status:** ✅ Built
**Priority:** High — typed handles with color-coded data types.

Wraps React Flow's `<Handle>` with data-type coloring and a hover tooltip. The handle's border color matches the data type (blue for number, purple for table, etc.). When connected, the handle fills with color and gets a subtle ring glow. On hover, a tooltip shows the label, data type dot, and required marker.
