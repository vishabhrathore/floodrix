## Manual patch — `CustomCodeHandler.ts`

Open `src/server/engine/handlers/CustomCodeHandler.ts`. You need to change how it evaluates code to use the worker pool. Find the `execute()` method and change the core evaluation block from:

```ts
const outputs = safeEvaluateMultiLine(code, scope, outputVarNames, {
    timeoutMs: config.timeoutMs ?? this.timeoutMs,
});
```

To:

```ts
import { WorkerPoolTimeout } from "../WorkerPoolTimeout"; // add at top of file

// inside execute():
const pool = new WorkerPoolTimeout();
const outputs: VariableMap = {};

// Worker evaluates one expression at a time; multi-line code is split
// and each assignment runs through the worker separately. This keeps
// the worker contract simple (single expression in, number out) and
// still gives us timeout isolation.
const lines = code.split(/\r?\n/).map(l => l.trim()).filter(Boolean);
const workingScope = { ...scope };

for (const line of lines) {
    const match = line.match(/^([a-zA-Z_][a-zA-Z0-9_]*)\s*=\s*(.+)$/);
    if (!match) continue;
    const [, varName, expr] = match;

    const result = await pool.runMathEvaluation(
        expr,
        workingScope,
        { timeoutMs: config.timeoutMs ?? this.timeoutMs, handlerType: "CUSTOM_CODE" }
    );

    if (typeof result === "number") {
        workingScope[varName] = result;
        if (outputVarNames.includes(varName)) {
            outputs[varName] = result;
        }
    }
}
```

The FORMULA and MULTI_FORMULA handlers keep using `safeEvaluate` — they have mathjs-level timeout already, and worker overhead isn't worth it for short expressions.

If you don't want to apply this patch right now, skip it. The worker_threads infrastructure still ships and you can adopt it later for specific handlers when a real runaway happens.

## Known sharp edges

**worker-mathjs-runner.js path resolution.** `WorkerPoolTimeout` uses `__dirname` + `join(__dirname, "worker-mathjs-runner.js")` to find the script. This works when Next.js compiles server code to CommonJS (which it does by default for API routes and tRPC handlers). If you're using a different setup — Bun, Deno, or Next.js with server actions on the Edge runtime — the path resolution will fail. In that case, either:

- Inline the worker code via `new Worker(new URL('./worker-mathjs-runner.js', import.meta.url))`, OR
- Use a bundler plugin to copy the .js file to the output next to the compiled .ts

**Worker startup cost.** Each `runMathEvaluation` call spawns a new worker (~10-50ms overhead). For high-throughput workflows with many CUSTOM_CODE nodes, you'd want a persistent worker pool that reuses threads. Skipped that for simplicity; the cost matters only if you're running hundreds of CUSTOM_CODE evaluations per second.

**Size estimate uses UTF-16 upper bound.** `estimateBytes` does `str.length * 2`. That's a correct upper bound for in-memory V8 representation but could be conservative (UTF-8 on disk is often smaller). If users are hitting the limit with payloads they think should fit, consider switching to `Buffer.byteLength(str, "utf8")`.

**TTL cutoffs are hardcoded.** `PAUSED_TTL_MS = 30 days`, `PENDING_TTL_MS = 6 hours` live as constants in `session-ttl-sweeper.ts`. If you want them configurable per-organization, move them to a settings table. For now, edit the constants directly if you need different values.

## Chunk 5 — Hardening

This is the "make it production-safe" chunk. Everything here is stuff you *can* ship without, but each piece closes a hole that would bite you in production.

### What's in it

**1. Session TTL cleanup cron** *(1 new file)*

- `src/inngest/functions/session-ttl-sweeper.ts` — runs hourly via Inngest cron
- Finds `PAUSED` sessions older than 7 days (configurable), marks them `TIMED_OUT`
- Also cleans up `PENDING` sessions older than 1 hour that never started
- Without this: a user starts Dicken's workflow, closes the tab at the INPUT pause, session sits in your DB forever. Over a year you accumulate thousands of dead rows.

**2. Handler timeouts via Workers** *(2 files)*

- Current handler timeout uses `Promise.race` with `setTimeout`. This *detects* a timeout but can't *cancel* the handler if it's stuck in synchronous JS.
- New: wrap handlers in `worker_threads` so truly runaway code (e.g., `CUSTOM_CODE` with `while(true){}`) gets killed, not just detected.
- `src/server/engine/WorkerPoolTimeout.ts` + one change in `WorkflowExecutor.ts`

**3. MetricsListener** *(1 new file)*

- `src/server/engine/listeners/MetricsListener.ts`
- Hooks into the event emitter, records: node duration histograms, handler error rates, strategy distribution, Inngest queue depth
- Writes to either `console.log` (dev) or a pluggable metrics sink (OpenTelemetry-compatible)
- Without this: when production slows down, you have no data to diagnose *why*

**4. Clock injection seams** *(small edits to 3 files)*

- `RunOrchestrator`, `SessionPoller`, and the TTL sweeper all currently use `new Date()` / `Date.now()` directly
- Thread the `Clock` interface that already exists in `types.ts` through these
- Makes testing retry behavior, TTL thresholds, and polling intervals *much* easier (no `jest.advanceTimersByTime` dances)
- Without this: any test involving time is flaky

**5. Schema `metadata` version guard** *(1 small edit to `SessionRepository.ts`)*

- We already have `METADATA_VERSION = 1` in `types.ts` and a `hydrateMetadata` function
- Add a migration path: if we ever bump to v2, old PAUSED sessions in the DB get forward-migrated transparently
- Currently the code throws if the metadata shape is wrong. After this edit, it logs and falls back to defaults.
- Without this: the day you rename a metadata field, every paused session in the DB breaks

**6. `stepBack` policy expansion** *(small edit to `WorkflowExecutor.ts`)*

- Chunk 3's `stepBack` has `IRREVERSIBLE_NODE_TYPES = new Set(["API_CALL", "PDF_REPORT"])`
- This adds an optional `isReplayable` flag on `NodeHandler` so individual handlers can declare themselves (e.g., API_CALL with `GET` is replayable; `POST` isn't)
- Fallback: if handler doesn't declare, use the current hardcoded set
- Without this: `stepBack` is either too permissive (re-charges cards) or too restrictive (blocks harmless GET replays)

**7. Variable store size enforcement** *(small edit to `VariableStore.ts`)*

- Chunk 1 defined `MAX_VARIABLE_BYTES` and `MAX_STORE_BYTES` constants but never enforced them
- Add enforcement in `set()` and `merge()` — throw clear error if exceeded
- Without this: a runaway `API_CALL` response could stuff 50MB into a variable, blow up DB writes and memory

**8. Subworkflow depth counter** *(placeholder — actually implemented in handler chunk)*

- Just a TODO comment in the executor for when SUBWORKFLOW handler lands
- Real implementation happens when you add the async handlers (Chunk 4.5)
- I'll skip this if you haven't done Chunk 4.5 yet
